## 初始化完成定义

初始化完成须证明桌面、API、worker、现场端、共享协议和数据库能够协作。订单 CLI 通过只属于其中一项，不能代替进程链路验收。真实模型 Key、真实打印机和完整业务功能不作为基础工程连通测试的前提。

## 初始化步骤与交付物

| 编号 | 工作 | 可审查交付物 | 验收 |
| --- | --- | --- | --- |
| B-01 | 建立 workspace | 四应用三公共包、依赖清单、锁文件、忽略规则 | 所有包可安装和导入，禁止依赖方向在静态检查中被发现 |
| B-02 | 固定配置与身份装配 | personal/enterprise 配置、工作区引用、密钥引用、Fake 模型/设备 | 非法配置明确失败，日志与前端不回显保存后的 Key |
| B-03 | 初始化持久层 | SQLite/PostgreSQL 迁移、持久任务、事件及 checkpoint 配置 | 两种数据库分别创建与升级；业务记录和队列不会只存在内存 |
| B-04 | 启动 API 与 worker | 健康检查、本地任务入口、企业 Celery 入口、受保护本机发现记录 | 提交诊断任务后 worker 执行并回传事件，重复提交不重复生效 |
| B-05 | 连通现场端 | 登记、领取、Fake 工具执行、结果与动作回执 | 版本/凭据不符被拒绝，正常任务能通过完整协议往返 |
| B-06 | 连通桌面 | main/preload/renderer、生成 SDK、模式选择与事件订阅 | 同一诊断任务从窗口提交并看到结果，不允许 renderer 直接调用硬件 |
| B-07 | 验证进程生命周期 | 单实例、启动/停止入口、关闭窗口行为、崩溃诊断 | 关窗任务继续，重开补读，后台异常留下可追查状态 |
| B-08 | 固定可复现入口 | 实际验证后的根级开发/构建/检查命令及 CI | 新开发环境按命令完成以上步骤，命令及预期输出随实现补齐 |

## 双模式连通场景

个人：桌面 → 本机认证 API → SQLite 持久任务 → 本地 worker/Fake 模型 → 本机现场端/Fake 工具 → 回执和事件 → 桌面；重开后读到同一任务。

企业：桌面 → 企业测试身份/API → PostgreSQL/outbox → Redis/Celery worker → 登记现场端/Fake 工具 → 持久结果与事件 → 桌面；另一无权限身份不能读取任务。

这两个场景只证明工程协作。真实 Orca、模型 API 兼容性、实物质量及正式安装包分别验收，不以 Fake 结果冒充已接通。

## 样例与 CLI
### 订单样例与开发 CLI

**交付：** 项目环境、统一入口和固定业务样例。

### 在当前项目完成

1. 配置 uv 与选定 Python 3.12 解释器，核对所需原生库的目标平台支持。
2. 建立固定 `apps/{desktop,api,worker,edge}` 与 `packages/{control-plane,contracts,sdk-ts}` workspace 配置，分组依赖并在安装验证后生成锁文件；业务 CLI 位于 `apps/api`，不使用根 `app/`。
3. 添加 `fixtures/orders/bracket-50-sets.json`、获准使用的底座/卡扣模型及配置清单。
4. 添加虚构设备、材料卷、验收规则和预期异常，不接真实设备。
5. 实现 CLI `show-order`，展示 50 个底座、100 个卡扣和资料缺项。
6. README 写明安装、样例来源与运行方式；忽略密钥、本地配置、运行数据和虚拟环境。

环境初始化：

```powershell
uv venv --python 3.12
```

本阶段完成并配置安装后应支持：

```powershell
uv sync --package autumn-api --extra local --dev
uv run --package autumn-api python -m autumn_api.cli show-order --fixture fixtures/orders/bracket-50-sets.json
uv run pytest
```
