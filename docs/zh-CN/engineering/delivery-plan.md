# 功能交付计划

[English](../../en/engineering/delivery-plan.md) | 简体中文

本文件只维护实现顺序、依赖和增量验收；完整功能由[功能规格](../product/functional-spec.md)定义，工程架构由[架构总览](../architecture/overview.md)与[仓库结构](../architecture/repository.md)定义。阶段不表示另建临时目录，也不改变两种模式共用业务实现的原则。当前均待实现。

## 开发约定

- **一个仓库、固定子项目。** 四应用三公共包按目录划分，分支用于开发和发布；API/worker 共用业务，edge 通过协议接入，不导入业务核心。
- **先有真实工具闭环。** 先确认 Orca 能对样件实际切片，再让 Agent 调用它。
- **模型推理有事实来源。** 尺寸来自几何工具，估算来自切片，设备状态来自连接器，质量来自真实检查。
- **区分估算、观测、假设和批准。** 不把建议参数写成已验证工艺，不把假设原因写成确定根因。
- **权限随数据和动作加入。** 后期完善组织治理，早期就限制文件、凭据和设备访问。
- **保留原始文件与历史。** 模型、有效配置、G-code、测量和批准记录均可追溯。
- **物理动作与软件重试分开。** 重跑切片和再次启动打印具有不同条件；外部结果未知时先核查。
- **累计验收。** 每阶段验证新增业务，也重跑上一版的订单流程。
- **完整目标结构、按功能验收。** 统一采用[仓库结构](../architecture/repository.md)中的目录，个人与企业用配置和 Adapter 区分，不建立临时目录或复制两套产品；文档目录不代表已有实现。

## 整体版本路线

| 阶段 | 新增能力 | 本版真正能做什么 |
| --- | --- | --- |
| 初始化 | 四应用、双模式、协议、持久化及样例 | 通过 B-01 至 B-08 工程连通门槛 |
| 1 | Orca 本地执行适配器 | 对一个模型真实切片并保存结果 |
| 2 | 受控单 Agent 与候选比较 | 根据需求比较少量实际切片方案 |
| 3 | Electron、账号、任务与文件持久化 | 在桌面工作台提交任务、看进度和历史 |
| 4 | 首件试打与实物验收 | 将候选方案推进到真实检查结果 |
| 5 | 工艺迭代、知识与版本批准 | 依据试验改进并保存适用工艺 |
| 6 | 多 Agent 与长任务恢复 | 分工调查，跨中断继续任务 |
| 7 | 单一设备生态接入 | 准备确认后执行获准的设备作业 |
| 8 | 批次、材料与生产计划 | 按已验证工艺安排一笔小批量订单 |
| 9 | 异常、补打与质量齐套 | 处理失败、返工和变更，算清合格缺口 |
| 10 | 企业治理与可靠执行 | 多角色协作、审批审计与执行运维 |
| 11 | 评估、部署与交付复盘 | 在新环境部署，验证恢复和真实业务结果 |

首期聚焦 FDM、一组可测试设备、喷嘴和材料组合，以及一类功能件。扩展材料、设备、多色或其他打印工艺时逐项验证。

## 工程初始化门槛

开始功能交付前，按[工程初始化](bootstrap.md)验证四应用、两种模式与协议链路。原阶段 0 的订单样例与 CLI 是初始化的一项；不能仅以 CLI 成功代替 B-01 至 B-08。

## 阶段 1：先接通真实 Orca 切片

**沿用：** 原有订单、模型、设备与配置样例。

**新增：** `SlicerGateway`、Orca 执行适配器、结果与配置快照。

### 在上一版上修改

1. 选择实际可运行的 OrcaSlicer 二进制，记录版本与来源；本地源码版本不等同于已安装程序版本。
2. 读取该二进制实际支持的帮助选项，用一个已知可切片模型验证输入、配置和输出。
3. 封装配置加载、模型检查、实际切片和结果读取；先只实现完成样例必需的能力。
4. 在独立任务目录保存输入、完整有效配置、引擎版本、输出、退出码、警告和耗时。
5. 对配置继承、机器与耗材兼容性进行验证；不假设不同版本的 CLI 语法一致。
6. 未提供结构化统计导出的版本采用经过测试的结果解析，并记录来源和单位；字段缺失标记未知。
7. 所有子进程参数通过结构化列表传递，限制工作目录、资源、超时和可访问文件。
8. 保存几何工具可计算的尺寸等结果，未实现的薄壁、支撑或强度分析不得声称已完成。

### 模型完整性检查与修复

导入后先生成检查报告，再决定是否允许进入切片。计划逐项接入以下检查，并标明每项是已检查、发现问题、无法判断还是当前工具未支持：

| 检查层级 | 检查内容 | 处理方式 |
| --- | --- | --- |
| 文件读取 | 解析失败、空模型、异常或缺失对象 | 阻止继续处理，指出对应文件与原因 |
| 网格完整性 | 孔洞、非流形边、退化面、异常法线、自交等 | 由实际几何工具检测，记录问题位置、数量及能力限制 |
| 部件结构 | 分离壳体、多部件与意外碎片 | 对照预期零件结构确认；分离部件不直接等于模型损坏 |
| 尺寸与设备 | 单位、缩放、尺寸包络与目标打印范围 | 单位不明时请求确认，超范围时阻止使用该设备方案 |
| 工艺风险 | 薄壁、悬空、支撑与关键表面等 | 按已实现算法和切片结果另行分析，不能用网格检查通过代替可打印性验证 |

修复通过 `GeometryGateway` 的受控能力执行，Agent 负责解释报告、提出修复计划和调用工具。首版先完成读取、尺寸和已选工具支持的网格检查，其余项目保留明确的未支持状态。

修复始终保留原件并生成新的 `ModelRevision`，保存所用工具/版本、修复选项、前后问题与几何差异。修复后重新检查；涉及表面、尺寸、部件或配合变化的结果由模型负责人确认后才能用于切片。工具不能可靠修复时，保留失败原因并请求人工处理。

本阶段实现后应支持：

```powershell
uv run --package autumn-api python -m autumn_api.cli slice --order fixtures/orders/bracket-50-sets.json --candidate baseline
```

### 累积验收

- [ ] 对真实模型实际切片，输出可在目标 Orca 版本打开检查。
- [ ] 时间、耗材等数值来自引擎结果，能定位对应配置与文件。
- [ ] 相同输入与有效配置可重复得到可比较结果，差异有记录。
- [ ] 超时、无效模型、配置不兼容和错误退出均有测试或可复现验证。
- [ ] 已支持的孔洞/拓扑问题能被样件验证；未支持项目不会被显示为检查通过。
- [ ] 修复保留原件与新版本，未确认的几何变化不会自动进入切片。
- [ ] 本阶段仅生成文件，不触发真实打印。

## 阶段 2：让单 Agent 比较实际工艺候选

**沿用：** 同一个 Orca 适配器与切片结果。

**新增：** 模型客户端、受控工具循环、候选计划和比较报告。

### 在上一版上修改

1. 建立统一配置、模型适配器、模拟模型与真实模型模式。
2. 注册读取订单、检查模型、提出修复计划、受控修复、查看配置、创建候选、执行切片和读取结果等工具；修复沿用阶段 1 的版本和确认规则。
3. 根据接触面、装配、材料和交期要求形成 2–3 个候选；初期只允许修改少量已验证参数。
4. 参数名、类型、范围、配置兼容性及组合约束由共用控制端校验，本地与企业使用同一规则。
5. 所有候选实际切片后再比较，报告包含参数差异、估算、警告、局限与需要试打的事项。
6. 增加步数、候选数、子进程并发、调用超时和费用预算上限。
7. 保留原有 CLI，通过 `analyze-order` 提交任务并观察结果；推理与工具编排仍由当前模式的 worker 执行，CLI 不另建 Agent 运行体系。

### 累积验收

- [ ] Agent 能对固定订单生成有实际数字的候选比较。
- [ ] 最快、最省料与表面要求有冲突时展示取舍，不伪造一个“全局最优”。
- [ ] 模拟模型可重复验证工具链；真实模型调用失败不会变成模拟成功。
- [ ] 不存在的工具、越界参数和引用不存在的切片结果会被拒绝。
- [ ] 输出明确哪些是切片估算，哪些仍需试打。

## 阶段 3：完善可持续使用的 Electron 业务工作台

**沿用：** 订单服务、Agent Runtime 与切片工具。

**新增：** 在已连通的双模式桌面与身份框架上加入完整业务任务、模型、成果和历史页面；基础运行链路沿用初始化结果。

### 在上一版上修改

1. 首次启动提供个人使用/连接企业。个人建立本机工作区与所有者，模型 Key 由本机受保护存储保存；企业接 OIDC 和资源授权，生产配置禁用开发身份入口。
2. 使用共用 SQLAlchemy 业务模型与 Alembic，个人 SQLite、企业 PostgreSQL 保存业务记录；分别验证事务与迁移，现场动作日志和 Agent checkpoint 独立管理。
3. 提供创建与查询任务、结果、事件和文件接口；长任务创建后立即返回编号。
4. 个人由本机 SQLite 持久队列 worker 执行有界任务，企业由 Linux Celery/Redis 与 PostgreSQL outbox 派发；两者使用相同 run/幂等语义，Orca 均由现场端执行。持久事件通过 SSE 进入 main 再转发界面。个人 API 只绑定受认证 loopback。
5. 页面包括订单输入、模型预览、候选比较、进度、切片成果和历史。
6. 上传、预览、下载与事件接口均校验资源权限；导入文件只能访问自己的工作区。
7. 页面展示输入/配置/引擎版本，能打开原始警告和工具错误。
8. 建立 main/preload/renderer 边界，采用命名且校验参数的 IPC；renderer 不持有设备凭据或直接启动 Python/Orca。
9. 使用 electron-vite + React/TypeScript + Three.js/R3F；通过 electron-builder 生成 Windows NSIS 测试包，提供受管理 Python 后台和运行依赖，验证个人模型连接、企业登录、文件导入与打包路径。终端用户不执行 uv/pnpm 命令。

### 累积验收

- [ ] 在 Electron 窗口完成已有订单的候选比较，CLI 继续可用。
- [ ] 重开窗口能恢复历史展示，事件重连不重复创建切片任务。
- [ ] 切片产物可以按权限下载，不能通过猜测 ID 读取其他空间文件。
- [ ] 进程异常留下的执行被明确标记，本阶段不宣称自动恢复。
- [ ] 实际安装包可启动；非法 IPC、越权文件与任意外链执行受到限制。
- [ ] 关闭窗口不取消后台任务；原生现场端由独立进程/服务管理。
- [ ] 干净 Windows 环境无需开发工具、数据库或 Redis，安装后配置模型 API 即可完成已有订单流程。
- [ ] 同一业务场景在本地 SQLite/持久队列和企业 PostgreSQL/Celery 上分别验收；工作区切换不串数据、凭据、事件或设备控制权。

## 阶段 4：把候选推进到首件试打和实物验收

**沿用：** 候选、切片结果、订单和工作台。

**新增：** 试打计划、人工执行记录、检查项与验收状态。

### 在上一版上修改

1. 从候选创建 Trial，记录目标、设备条件、材料、喷嘴、文件与待检查事项。
2. 试打先由操作者在原有 Orca/设备界面执行，再回填实际作业和结果；此时不要求远程控制。
3. 页面提供照片、实测尺寸、装配反馈、表面检查、失败描述与附件。
4. 计划检查项区分已测、未测、无法判断和不适用，记录操作者与时间。
5. 首件结论由有权限人员确认，不能由照片自动补造卡尺测量或装配结果。
6. 维护打印完成、待验收、通过、不通过、待补资料等不同状态。

### 累积验收

- [ ] 同一候选能产生试打和真实检查记录，回链到切片与配置。
- [ ] 卡扣装配过紧时留下不通过和证据，不进入批量批准。
- [ ] 没有测量记录的检查项保持未知或待检。
- [ ] 重复上传结果不会重复增加订单合格数量。
- [ ] 模拟数据演示与真实实物记录在页面有明确标识。

## 阶段 5：用试验改进工艺，建立经过确认的版本

**沿用：** 首件问题、测量、配置和切片工具。

**新增：** 原因假设、对照试验、工艺知识检索与版本批准。

### 在上一版上修改

1. 按问题整理已知事实、可能原因、缺失信息和下一项检查。
2. 先接入已选版本 Orca 文档、设备/耗材资料和历史试打记录，保存来源、版本与适用条件。
3. 对少量因素安排可解释试验，不在一次试打中随意修改大量参数。
4. 如需温度、PA、流量或回抽等校准，复用对应版本实际支持的流程；不能默认所有校准都有统一 CLI。
5. 比较实际测量和装配结果，报告支持或反驳哪些假设，资料不足时继续待确认。
6. 批准后生成 `ValidatedProcess`，固定模型、有效配置、引擎、设备条件、材料与验收证据。
7. 模型、喷嘴、设备或材料条件变化时，按明确策略提示需复核或重新验证。

### 累积验收

- [ ] 能沿用首件问题完成一轮有证据的试验，保存前后变化。
- [ ] 文档建议与实际验证结论分别显示；历史经验不能自动写成当前事实。
- [ ] 未通过或未检查完整的工艺不能被标记为已批准。
- [ ] 已批准版本不被后续编辑覆盖，撤销与重新批准保留历史。
- [ ] 知识检索使用当前用户有权访问的记录。

## 阶段 6：加入多 Agent 分工和长任务恢复

**沿用：** 全部工具、试验、知识与工艺对象。

**新增：** 任务计划、受限委派、持久执行状态与用户等待。

### 在上一版上修改

1. 根据任务需要分派需求核对、几何检查、工艺比较、试验分析和结果复核。
2. 每个子任务明确输入、可用工具、预算、依赖和完成证据，权限不高于主任务。
3. 独立调查可以并行，同一配置或成果的写入有协调；简单查询保持单 Agent 执行。
4. 用选定的图执行实现管理计划、分支、退回、等待、取消与恢复，保留原有业务接口。
5. 共用同一套角色、工具与图版本；个人 SQLite checkpoint，企业 PostgreSQL checkpoint。任务、步骤和事件持久化并关联，恢复核对业务幂等记录，不假定 checkpoint 与业务数据库原子提交。
6. 为切片重试、模型调用重试、人工试打和外部设备动作分别定义策略。
7. 用户补充验收条件时，定位受影响候选、试验和批准状态，不重做所有无关工作。

### 累积验收

- [ ] 可看到真实分工、失败、证据与汇总，子 Agent 的自报完成需检查。
- [ ] 审核回退和委派有次数、并发和预算上限。
- [ ] 已保存执行边界后停止服务，重启可继续同一任务。
- [ ] 等待实物测量时可跨重启保留，补充后继续原流程。
- [ ] 未知外部结果不会在恢复时无条件重发。

## 阶段 7：接入一个可验证的设备生态

**沿用：** 已批准工艺、任务权限和持久执行记录。

**新增：** `PrinterGateway`、设备状态、动作预览和结果核验。

### 在上一版上修改

1. 选择一组实际可测试设备和一个后端，核验查询、上传、开始、暂停、取消各项支持范围。
2. 首先接只读状态，显示在线、忙碌、故障及能力未知等情况。
3. 上传文件、启动打印分别记录动作；执行前确认获准工艺、目标机器、喷嘴、实际材料和文件哈希。
4. 操作者确认床面、装料和其他准备条件，批准绑定具体作业与版本。
5. 启动前再次读取设备状态，防止批准后设备被其他人占用。
6. 外部请求使用幂等标识或结果查询；超时进入待核查，不能直接假定失败并重发。
7. 保留原始设备事件与标准化状态，不能把同名机型自动视为全功能兼容。

### 发送打印的三种模式

| 模式 | 用户要求 | 系统应记录什么 |
| --- | --- | --- |
| 仅上传 | 把已确认的切片文件发送到指定设备，稍后人工启动 | 目标设备、远端文件标识、上传结果；不标记已开始打印 |
| 加入队列 | 将作业交给支持排队的设备后端 | 队列标识、等待条件与后续状态；不假定已占用设备 |
| 上传并开始 | 准备与授权均确认后立即执行 | 上传结果、启动请求、设备实际响应和对应作业标识 |

页面只展示当前适配器已验证支持的模式。打印过程继续查询状态与进度，按设备能力提供暂停、取消和继续；请求已发送与动作已生效分别显示，结果未知时先核查。

### 累积验收

- [ ] 在获准测试设备上完成一次可追溯作业，文件与已批准版本一致。
- [ ] 设备忙、材料/喷嘴不符、准备未确认时阻止启动。
- [ ] 上传成功不会被写成打印成功；实际执行有回读结果。
- [ ] 重复点击、超时与恢复不会无条件重复开打。
- [ ] 设备完成后进入待取件/待检验，后续清床另行确认。

## 阶段 8：用已验证工艺推进小批量生产

**沿用：** 固定订单、工艺版本、设备和材料记录。

**新增：** 批次、产能计划、材料余量和生产看板。

### 在上一版上修改

1. 按订单行、套件、首件计入规则和已验收数量计算剩余需求。
2. 将需求拆成批次与盘，记录每盘计划零件、数量、工艺版本和目标设备。
3. 按设备兼容性、实际材料、可用时间、清床与后处理资源提出计划。
4. 交期估算保留假设和不确定性，实际失败率没有数据时不能编造精确良率。
5. 生产看板展示待准备、可执行、打印中、待取件、待检、合格和异常。
6. 分配到其他机器或换料时检查工艺适用范围，必要时回到试打确认。
7. 实际产出、消耗和工时分别记录；切片估算用于对比，不覆盖真实记录。

### 累积验收

- [ ] 同一笔 50 套订单可以拆成多个可追踪批次。
- [ ] 材料不足、机器占用和人员不值守会形成可解释的计划阻塞。
- [ ] 不把尚未质检的计划数量算进合格库存。
- [ ] 工艺适用条件变化后不会继续静默使用旧文件。
- [ ] 持久化历史能回答每盘对应的订单、配置、设备和材料。

## 阶段 9：异常、补打、模型变更与齐套验收

**沿用：** 批次、设备记录、实物检查与订单数量。

**新增：** 异常案件、缺口计算、返工补打与交付状态。

### 在上一版上修改

1. 从人工上报或已核验能力的监控来源建立 Incident，关联照片、日志、原作业和影响范围。
2. 视觉异常只作为观察或假设；确定根因需要相应检查与证据。
3. 将受影响实物划为待检、可用、返工或报废，保留原记录和处理理由。
4. 按每个零件的实际合格缺口提出补打，区分原任务重试与新生产作业。
5. 客户修改卡扣模型时，标记受影响切片、工艺、排产和旧版实物；能否继续使用由负责人确认。
6. 对返工、重新检验和批准撤销做数量核对，避免重复记账。
7. 只有 50 个合格底座和 100 个合格卡扣等条件满足，才进入齐套检查；随后确认后处理、包装和交接。

### 累积验收

- [ ] 能演示一盘部分失败，正确保留可用数量并补齐缺口。
- [ ] 打印件总数相同但零件比例错误时，订单仍显示未齐套。
- [ ] 模型改版能找到受影响对象，旧版件不会自动冒充新版合格件。
- [ ] 重复监控事件、重复验收和重复审批不增加产出或重复下发。
- [ ] 可从交付记录追溯到模型、工艺、批次、材料与检查结果。

## 阶段 10：完善团队治理与可靠执行服务

**沿用：** 已有资源权限、动作批准、任务恢复和审计关联。

**新增：** 企业角色管理、正式身份配置、执行运维与资源控制界面。

### 在上一版上修改

1. 明确操作员、工艺负责人、质检员、订单管理员与系统管理员的权限，审批规则按组织配置。
2. 接入正式身份管理，生产环境停用开发身份；需要时支持企业单点登录。
3. 完善 PostgreSQL 约束、事务和迁移，检查模型、文件、工艺、事件和数量记录的关联。
4. 完善企业 Linux Celery worker、个人本地后台和原生现场端的运维、版本协商与恢复；API 保留提交、查询和控制职责，桌面窗口不承担任务生命周期。
5. 实现可靠派发、领取、租约、超时与并发；设备动作恢复仍先核查外部结果。
6. 限制可用模型、工具、运行资源、并发与费用；连接凭据由适配器使用，不进入模型消息或普通日志。
7. 审计覆盖工艺批准、模型替换、质检更正、设备动作、补打和权限变化。
8. 多组织部署时，验证数据库、文件、检索、缓存、checkpoint、日志与设备凭据的隔离。

### 累积验收

- [ ] 用户只能访问与操作授权订单、工艺和设备。
- [ ] 角色或权限撤销影响后续访问、审批与任务执行。
- [ ] API 与 worker 可分别重启，已提交任务不永久遗失。
- [ ] 租约回收和消息重投受幂等保护，物理动作不会被普通重试策略反复触发。
- [ ] 可以按订单、人员、工艺和设备追踪关键决定与实际结果。

## 阶段 11：评估、部署与实际交付复盘

**沿用：** 可完成整笔订单的应用及各阶段验证。

**新增：** 固定评估集、CI、部署、备份恢复和业务指标。

### 在上一版上修改

1. 固定样件与预期检查：正常模型、单位不明、损坏网格、配置不兼容、可见工艺取舍等。
2. 固定业务事件：首件不通过、材料不足、设备忙、启动回执未知、部分失败、模型改版和数量不齐。
3. 模拟模型与模拟设备用于自动化流程验证；真实 Orca 样件验证、真实设备试打和实物检查分别保留记录。
4. 不通过逐字比较模型回复来判断成功，检查工具事实、文件、配置、状态、数量和引用。
5. 记录估算与实际的时间/耗材偏差、首件试验次数、报废返工、缺口准确性、重复动作与人工投入。
6. 成本拆分实际材料、机时、人工、后处理和损耗；使用引擎成本时核查其组成，避免重复计入机时。
7. 提供部署、数据库迁移、文件存储、引擎版本、配置备份、凭据、健康检查和回滚说明。
8. 分别演练个人离线依赖安装/SQLite 备份与企业部署/PostgreSQL 恢复，以及休眠、后台中断和设备离线。个人转企业显式导出/导入，不携带凭据、活跃任务或未经企业复核的生产授权。
9. 完善 Windows NSIS 安装、签名与 electron-updater 更新链，验证服务端/现场端兼容性；在途作业期间不自动退出或替换执行端。

### 最终累积验收

- [ ] README 能指导新环境启动，演示、真实切片与设备模式分别说明。
- [ ] 一笔订单可从模型导入推进到首件、批次、异常、补打和齐套交付。
- [ ] 每个关键结论都能定位到工具结果、实测或人员确认。
- [ ] 已批准工艺的适用范围与版本可查，条件变化会触发复核。
- [ ] 软件完成、设备完成、实物质量和订单交付状态独立且关联正确。
- [ ] 有多角色权限、动作批准、审计、恢复与外部结果核查。
- [ ] 数量、版本、重复事件与重复动作有自动化覆盖。
- [ ] 有实际样件和实物验证记录，未知质量与未完成验证不会被伪装成成功。
- [ ] 已演练备份、恢复与回滚，剩余限制在文档中可见。
- [ ] 个人安装即用与企业服务器部署各自验收；本地/企业共用 Agent 契约评估，功能差异仅来自能力、资料、权限及组织协作配置。

## 每次开发如何保证真正集成

1. 先跑上一版订单主线，确认已有能力可用。
2. 选择一项具体增量，例如“首件不通过后可以关联新候选”。
3. 接通对应数据、工具、权限、任务和页面。
4. 验证新增路径及旧流程，特别检查版本、数量与物理动作状态。
5. 更新 README 中当前真正可用的命令、配置、限制与演示方式。
6. 留下一个可运行提交，再进入下一项增量。

阶段完成时要回答：订单推进到了哪里？事实依据在哪里？现在等待谁？哪些条件变化会让已有结果需要复核？下一次打开项目能否继续？

整个路线最终交付同一个 3D 打印工艺与生产应用，各阶段都围绕真实切片、实际验证和业务结果逐步完善。
